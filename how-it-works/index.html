Product guide

Evidence first.
Then a result.

Synapse Guard applies deterministic rules to the draft and records you supply. It does not retrieve Jira or calendar records automatically in the public demo.

Start with a synthetic example

Open the browser checker, choose “Load synthetic sample,” and run the check. The sample combines one blocked ticket, one explicit meeting overlap, and a confirmed empty attachment list. It is fictional and labeled as a sample.

Check your own evidence

Replace the draft and the Evidence JSON with only the records relevant to your message. Retrieve those records through a source you are authorized to use. Preserve real IDs, HTTPS source links, and the time the source was read.

{
  "tickets": [{
    "id": "TEAM-123",
    "title": "Your ticket title",
    "status": "blocked",
    "source_url": "https://your-team.atlassian.net/browse/TEAM-123",
    "retrieved_at": "2026-10-11T12:00:00Z"
  }]
}

This is a schema example. Replace every value with your actual source evidence; the example timestamp becomes stale. A status must be blocked, in_progress, done, cancelled, or unknown. Keep unsupported provider statuses as unknown.

A record is not a complete calendar read

Meeting checks require start and end times with explicit UTC offsets. Calendar coverage must state the retrieved interval, retrieval timestamp, and whether the read completed. An event list alone does not prove availability; missing, stale, or narrower coverage remains incomplete.

Distinguish unknown from empty attachments

Omit attachments if you do not know what is attached. Use "attachments": [] only after confirming that the outgoing draft has no attachments. Supply exact names for attached files. Synapse Guard does not inspect document contents.

Read the limits before acting

Findings identify possible conflicts for human review. The checker cannot verify all facts, understand every phrasing, prove a delivery deadline, or certify a message as safe. It never sends the draft or changes a source system.
